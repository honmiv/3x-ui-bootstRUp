3x-ui bootstRUp

Automated setup of a self-steal VLESS+REALITY (TCP/xhttp) configuration on 3x-ui. VPN connections, the admin panel, subscriptions, and regular HTTPS traffic share one domain and one port.

Installation

Automatic

curl -fsSL https://raw.githubusercontent.com/honmiv/3x-ui-bootstRUp/master/install.sh | bash

Manual

git clone https://github.com/honmiv/3x-ui-bootstRUp.git
cd 3x-ui-bootstRUp
./install.sh

Updates

Update script sources

Automatically pull the latest repository files:

curl -fsSL https://raw.githubusercontent.com/honmiv/3x-ui-bootstRUp/master/update_sources.sh | bash

Manual option:

git fetch origin
git reset --hard origin/master

Update the panel

To update the panel to a specific version:

./update.sh 3.3.1

To update the panel to the latest version:

./update.sh latest

Rollback

If something breaks after the update:

./rollback_update.sh

Requirements

  • OS: Ubuntu 26.04, Debian 13, CentOS 9.
  • Domain: point the domain name to the VPS IP address.
  • DNS: use an A record for IPv4 and an AAAA record for IPv6 if the provider assigns IPv6.
  • Ports: `80` and `443` must be free.
  • Dependencies: `curl` must be installed.

Architecture

All entry points: VPN, web panel, subscriptions, and fallback site use one domain with a single SNI (`sni=domain`). Caddy manages TLS certificate issuance and renewal automatically.

  1. The incoming request reaches Caddy at `domain:443`.
  2. Caddy routes traffic to the 3x-ui VLESS + TCP + Reality inbound without terminating TLS.
  3. If the request is not a TCP client connection, it is redirected to the VLESS + xhttp + Reality inbound.
  4. If the request is not an xhttp connection, TLS is still not terminated and traffic is redirected back to the internal Caddy port.
  5. On the internal port, Caddy terminates TLS. Decrypted HTTP traffic is routed to the 3x-ui panel, subscriptions, or Nginx:80.

For DPI systems, any unauthorized request looks like a standard HTTPS website request.

Client / DPI -> Caddy:443 -> VLESS TCP Reality -> VLESS xhttp Reality -> Internal Caddy -> 3x-ui panel / subscriptions / Nginx fallback
Client HTTP -> Caddy:80 -> HTTPS redirect or Nginx fallback

How setup.sh works

Environment checks and dependencies

  • Checks for `root` privileges.
  • Detects the package manager (`apt`, `dnf`, `yum`, `pacman`) and waits for package locks to clear.
  • Installs missing utilities such as jq, openssl, ss, qrencode, and others.
  • Installs Docker and Docker Compose if they are missing. For users in Russia, it configures the fallback registry mirror `dh-mirror.gitverse.ru`.

Dynamic configuration generation

  • Selects free internal ports, generates X25519 keys, and creates secure URL paths for the panel and subscriptions.
  • Processes templates from `templates` and turns them into working configuration files.

3x-ui automation

  • Starts the 3x-ui container and configures it through the API.
  • Prompts for the node type (foreign "freedom" or local "proxy") and automatically configures the corresponding Xray routing rules.
  • Updates admin credentials, applies routing paths, creates VLESS TCP and xhttp Reality inbounds, and adds a VPN client.

Validation and integration

  • Uses a pre-built Caddy image with L4 support from ghcr.io for faster installation (instead of building locally).
  • Starts Caddy and waits for successful SSL/TLS certificate issuance.
  • Checks HTTPS availability on port 443.
  • Retrieves and decodes subscription data, then prints connection links and QR codes.
  • Adds `/etc/profile.d/3x-ui.sh`, which displays the panel URL and credentials on each SSH login.

Notes

  • Non-target traffic redirection between inbounds uses the `target` field, not the `fallbacks` mechanism from recent 3x-ui versions.
  • Adding or removing inbounds requires careful `target` configuration.
  • Removing the `vless+tcp+reality` inbound without adding another inbound on the same port requires Caddyfile changes.
