# Сквозные VPN E2E тесты (VPN End-to-End Test Suite)

В данной директории находятся сквозные тесты сетевой связности (VPN End-to-End), проверяющие реальную доставку подписок, установку VLESS Reality туннелей и прохождение пользовательского трафика через развёрнутую инфраструктуру.

---

## 🎯 Главный инвариант и суть тестов

Основное требование ко всем тестам в этой папке — **проверка реального физического маршрута трафика**. 

Тест считается успешным **только** тогда, когда соблюдается полная цепочка:
$$\text{Клиент} \longrightarrow \text{Получение подписки} \longrightarrow \text{Нода 1 (Proxy)} \longrightarrow \text{Нода 2 (Freedom)} \longrightarrow \text{Целевой сервер (Echo)}$$

В ответе эхо-сервера **обязательно проверяется IP-адрес источника (`client_ip`)**:
- Запрос на эхо-сервер должен прийти с **выходной VPN-ноды** (Freedom-ноды), а **не** напрямую от тестового клиента или раннера!
- Если адрес в ответе эхо-сервера не совпадает с IP-адресом соответствующей ноды в сети `testnet`, тест завершается с ошибкой.

## 🏗 Архитектура тестового стенда

Для воспроизведения реальной работы клиента и целевых серверов в Docker-in-Docker задействованы:

│  │ • SOCKS5 :10808       │         │ • Домены: echo.test, ru.test         │  │

### 1. Эхо-сервер (`echo_server.py`)
- Легковесный HTTP-сервер на Python 3.12 (`echo-server` в `docker-compose.test.yml`), доступный в сети `testnet` по алиасам `echo.test` и `ru.test`.
- При обращении к `/ip` возвращает JSON с сетевыми параметрами:
  ```json
  {
    "client_ip": "172.18.0.11",
    "host": "echo.test",
    "headers": { ... }
  }
  ```
- Позволяет со 100% точностью определить, какой именно хост совершил исходящий сетевой запрос к целевому сайту.

### 2. Эмуляция клиента XRay (`vps-test-client-*`)
- В тесте не используются моки протоколов: запускается настоящий бинарник XRay Core в контейнере `ghcr.io/xtls/xray-core:latest`.
- Конфигурация клиента формируется динамически (`generate_xray_client_config()` в `tests/helpers.py`) на основе данных, распарсенных из реальной ссылки `vless://`:
  - UUID клиента
  - Публичный ключ Reality (`pbk`), Short ID (`sid`), SNI
  - Протокол передачи (TCP Reality либо XHTTP Reality)
- Клиент поднимает локальный SOCKS5-интерфейс на порту 10808.

### 3. Выполнение запроса (`query_echo_server_via_vpn`)
- Запрос выполняется через `curl` с одного из контейнеров-раннеров:
  ```bash
  curl -s --socks5-hostname vps-test-client:10808 http://echo.test/ip
  ```
- Использование `--socks5-hostname` гарантирует, что DNS-резолвинг доменов `echo.test` и `ru.test` выполняется удалённо на стороне выходного XRay узла.

## ⚙️ Допущения и адаптации для DinD

### 1. Маршрутизация трафика в тестовой сети (Split Routing)
- **Проблема в продакшене**: Маршрутизация на Proxy-ноде разделяет трафик по базам `geoip:ru` и `geosite:category-ru`. В тестовой среде DinD все контейнеры имеют локальные IP (`172.18.0.0/16`), а домены имеют псевдо-зону `.test`. Стандартный GeoIP не знает про адреса тестовой сети и направил бы весь трафик не туда.
- **Решение**:
  - В тестовом шаблоне `tests/overrides/panel/templates/3x-ui/xray-proxy.json.template` правила маршрутизации адаптированы для тестового окружения:
    ```json
    {
      "rules": [
        {
          "type": "field",
          "domain": ["domain:ru.test"],
          "outboundTag": "direct"
        },
        {
          "type": "field",
          "network": "tcp,udp",
          "outboundTag": "{{SUB_OUTBOUND_TAG}}"
        }
      ]
    }
    ```
  - Это позволяет строго протестировать разделение трафика:
    - Запросы на `ru.test` идут напрямую через Proxy-ноду (`direct`), и эхо-сервер видит IP Proxy-ноды.
    - Все остальные запросы (`echo.test`) заворачиваются в каскадный туннель на Freedom-ноду (`{{SUB_OUTBOUND_TAG}}`), и эхо-сервер видит IP Freedom-ноды.

### 2. Сквозной забор подписки через Caddy TLS
- Клиентский профиль перед тестированием туннеля скачивается с Caddy HTTPS через `fetch_subscription_via_host_tls()`.
- Проверяется не только сам туннель, но и возможность клиентского приложения получить актуальную конфигурацию по HTTPS.

### 3. VLESS Reality поверх Caddy L4
- Внутри виртуального VPS трафик порта 443 принимает Caddy с модулем Layer 4 (`caddy-l4`).
- Caddy по SNI проксирует зашифрованный Reality-трафик во внутренний порт `TCP_REALITY_INBOUND_PORT` или `XHTTP_REALITY_INBOUND_PORT` контейнера `3xui`.
- В тестах подтверждается корректность рукопожатия Reality через Caddy L4.

### 4. Известное ограничение: XHTTP Reality туннель не тестируется сквозным трафиком

Во всех VPN E2E тестах реальный XRay-клиент поднимается **только через TCP Reality**.

**Причина**: Caddy L4 на порту `:443` форвардит всё входящее сырое TLS-TCP соединение напрямую в `TCP_REALITY_INBOUND_PORT` контейнера `3xui`. XHTTP-инбаунд (`XHTTP_REALITY_INBOUND_PORT`) живёт на отдельном внутреннем порту и **не имеет прямой точки входа снаружи** — он недостижим из тестовой сети без изменения топологии (например, проброса порта в `docker-compose.test.yml`, что нарушило бы соответствие продакшн-конфигурации).

Что проверяется для XHTTP: каждый тест скачивает XHTTP-подписку по HTTPS и убеждается, что она возвращает статус `200` и корректную `vless://`-ссылку с `type=xhttp`. Тем самым проверяется, что XHTTP-инбаунд **создан и настроен корректно**, а подписка на него доступна через Caddy.

Что **не** проверяется: реальная передача пользовательского трафика через XHTTP Reality туннель. Это gap в покрытии, зафиксированный намеренно.
